# Two-operator overhaul: codebase review

Reviewed 2026-09-05 against commit `b4241a8` and the working tree. This is a review of the proposed implementation, not certification of a completed overhaul. The original spec is available in that commit; the revised [spec](../specs/two-operator-overhaul-spec.md) incorporates the corrections below.

## Verdict

The original spec is not safe to implement verbatim. The main blockers are concurrent inventory writes, nested commits, undefined retry behavior, incomplete authorization, and assumptions about replacing the database driver. The product workflows fit the application once those foundations and the missing integration points are addressed.

Recommended rollout: preserve the existing cloud-authoritative model for the first two-operator release, make each business operation atomic and retry-safe, then evaluate offline writes separately. Offline operation remains a product objective. Deferring it is a review recommendation, not a claim that the owner has approved a scope change. If offline stock changes are mandatory at launch, TASK-8 becomes a blocking architecture project.

## Verification performed

Read the original spec, schema, database adapter, startup and packaging files; all existing route families; item and metadata models; stock and barcode services; React providers, API services/hooks, scanner, inventory interactions and report/print consumers. Used the existing graph as an orientation aid, then checked source directly. The bounded movement graph query was truncated; it was not treated as an exhaustive dependency inventory.

Executed the actual `record_quantity_adjustment()` service with only `get_db()` replaced by an in-memory SQLite connection loaded from the repository schema:

1. Start at 10; add 3 for a first simulated receipt line; fail the second line using a nonexistent item; call outer rollback. Balance remains **13**, with **one committed log**. This reproduces R02.
2. Call the existing helper with type `return`, quantity 2. Balance becomes **11**, reproducing R03's wrong-direction risk.
3. Call it with type `removal`, quantity -3. Balance becomes **14**, reproducing R03's validation gap.
4. The daily summary counts the Addition and Removal entries, but does not include Return.

These demonstrate current helper behavior, not execution of the unimplemented PO or ticket APIs. No production database was queried or changed. No overhaul runtime files were modified. The review environment has no project Python virtualenv or frontend `node_modules`; frontend compilation, packaged Windows behavior and real two-device Turso behavior were not verified. The schema contracts and release tests in the revised spec remain implementation work.

A nearby existing defect is also visible: `movement_log_model.py` catches `sqlite3.Error` without importing `sqlite3`. Its error path should be covered while changing summary logic. Broad item-create ValueError handling also assumes a matching duplicate exists; new validation must not turn malformed input into a secondary exception.

## External verification

The current Turso documentation describes last-push-wins conflict resolution and replay of local changes on pull. Applied to this application's absolute stock assignments, that supports R01's lost-update risk; this is an engineering inference, not a test against the production database. [Turso conflict resolution](https://docs.turso.tech/sync/conflict-resolution).

The sync usage documentation describes first-run bootstrap requiring remote availability and explicit push/pull operations. Initial offline launch and ongoing offline launch therefore need separate acceptance tests. [Turso sync usage](https://docs.turso.tech/sync/usage).

The Python reference distinguishes the Turso and libSQL engines and their drivers. A dependency replacement must verify the deployed engine and pinned package rather than treating the names as interchangeable. [Turso Python reference](https://docs.turso.tech/sdk/python/reference).

## Owner-facing product assumptions

The revised spec labels the following choices as review defaults: online authoritative first release; one final PO receipt; expiry after 48 hours; office and warehouse may close tickets; manual close with outstanding stock is a disposition, not a stock movement; late returns remain possible with an audit trail; new POs select existing active inventory items. These resolve ambiguity for implementation planning but should be confirmed in product acceptance. Offline launch requirements and a strict workstation security boundary materially change architecture.
